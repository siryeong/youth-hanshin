# 4단계 운영 구현

전체 관리자는 `/operations`에서 명단·기수·마을 편성과 카페를 관리합니다. 로그인한 사용자는 `/announcements`에서 전체 소식을 조회합니다. 사용자 승인으로 운영 DB에 `0011_operations.sql`까지 반영했습니다.

## 결정과 이유

| 결정 | 이유 |
|---|---|
| 1년 이상 미접속자를 별도 조회하고 계정·명단·배정 유지 | 사용자 결정. 새 기수에서도 장기 미접속자를 편성 대상에 포함 |
| 마지막 접속 기록이 없으면 등록 시각으로 장기 미접속 판단 | 한 번도 로그인하지 않은 인원도 같은 기준으로 관리 |
| 전체 명단과 마을별 편성 화면 분리 | [Planning Center People](https://www.planningcenter.com/people)의 인원 목록 관리와 기존 `design/Assign.dc.html` 적용 |
| 직접 등록 명단은 선택적인 `auth_user_id`로 인증 계정과 구분 | 미가입 인원도 출석·편성에 포함. 공유 중인 v1 인증 계정을 만들거나 삭제하지 않음 |
| 삭제는 장기 미접속 상태가 아닌 직접 등록 명단에만 허용 | 잘못 등록한 항목을 정리하면서 가입 계정과 장기 미접속자 보존. 직접 등록 명단과 이후 가입한 계정을 자동 병합하지 않음 |
| 새 기수 생성 시 현재 기수 전환·전체 인원 미배정을 한 트랜잭션으로 처리 | 전환 중 편성 충돌 방지와 지난 기수 기록 보존. 기존 기수보다 이후 연도만 생성 |
| 기수·배정 변경은 RPC, 메뉴·소식 변경은 RLS 적용 | 지난 기수 변경 차단과 목회자 전용 역할 지정 보장 |
| [HTML Drag and Drop](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API)과 선택 후 이동 | 새 의존성 없이 데스크톱 드래그와 터치·키보드 조작 지원 |
| 생년월일 미입력은 평균에서 제외, 남·여·미상 수 표시 | 모르는 값을 0세나 특정 성별로 집계하지 않음 |
| 출석·주문·소식·기도제목이 있는 마을의 삭제 차단 | 기록 보존. 기록이 없는 마을은 인원을 미배정으로 옮긴 뒤 삭제 |
| 주문 당시 마을 기준 개인 목록과 메뉴·옵션별 수량 집계 | 인원 이동 후 집계 일관성 유지. 취소 항목은 수량 집계에서 제외 |
| 기존 소식 편집기를 공용 `MessageBoard`로 이동 | 마을 소식·기도제목·전체 소식의 입력 보존과 삭제 확인 재사용 |
| 본인 프로필 변경 번호로 운영 캐시 갱신, 카페에는 공개 변경 번호 사용 | [Supabase Realtime](https://supabase.com/docs/guides/realtime/postgres-changes)의 RLS를 유지하면서 게스트에게 가격 없이 카페 변경 전달 |

## 검증과 반영

추가 마이그레이션은 `0011_operations.sql`입니다. 권한·기수 보관·휴면 인원 재편성·메뉴 스냅샷·카페 제약은 `npm run test:db:local`로 검증합니다. 실행 중인 로컬 DB에 트랜잭션으로 적용한 뒤 롤백하므로 운영 접속과 DB 초기화가 필요하지 않습니다.

`npm run test:ui`는 합성 데이터로 명단 마스킹·저장 실패 시 입력 보존·드래그와 선택 이동·목회자와 임원 권한·다음 기수 편성·카페 설정·전체 소식을 검증합니다. 실제 카카오 인증과 Realtime 전송은 이 브라우저 검증에 포함하지 않습니다.

로컬 앱에서 사용하려면 로컬 Supabase에 `0011_operations.sql`까지 적용합니다. 운영 DB에는 `supabase db push`로 `0011_operations.sql`을 적용했습니다. 배포 설정과 공유 인증 계정은 변경하지 않았습니다. 웹 배포 상태는 별도 확인이 필요하며, 푸시 알림과 PWA는 5단계 범위입니다.
