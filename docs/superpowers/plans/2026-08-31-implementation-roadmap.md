# 청년부 통합 플랫폼 구현 로드맵

**스펙:** `요구사항.md`
**디자인 시스템:** `design/` (아트보드 소스), 캔버스 https://claude.ai/code/artifact/6e4bb82b-f794-4907-9579-393d03e9b285

이 문서는 단계 구분과 그 근거만 담는다. 단계별 실행 계획은 `docs/superpowers/plans/`에 단계마다 따로 쓴다.

## 원칙

- 엔드투엔드로 동작하는 최소 버전에서 시작해 단계마다 기능을 얹는다. 각 단계는 그 자체로 배포 가능해야 한다.
- 권한 검증은 DB에서 한다. UI 비활성화는 보조 수단이다.
- 되돌리기 어려운 판단(스키마, 권한 모델, 토큰 체계)은 1단계에서 확정한다.

## 기술 결정

| 결정 | 이유 |
|---|---|
| React 19 + TypeScript + Vite | 요구사항의 스택. Vercel 배포와 궁합이 맞고 설정이 가장 적다 |
| React Router v7 (declarative) | 역할별 라우트 가드가 필요하다. 파일 기반 라우팅까지는 필요 없다 |
| TanStack Query v5 + Supabase Realtime | "마을명 변경·주문 취소·인원 이동은 전 화면에 즉시 반영" 요구를 캐시 무효화 한 곳에서 처리한다 |
| CSS 커스텀 프로퍼티(`tokens.css`) + CSS Modules | 디자인 시스템이 "같은 토큰 이름에 값만 바꿔 끼운다"로 설계돼 있다. `[data-theme]`로 변수만 덮으면 다크 테마가 끝난다. 유틸리티 프레임워크를 넣으면 토큰 정의가 두 곳(설정 파일 + CSS)으로 갈라진다 |
| zod | 생년월일·휴대폰 형식 검증. 폼 라이브러리는 폼이 늘어나기 전까지 넣지 않는다 |
| @dnd-kit/core | 마을 편성 드래그앤드롭. 터치와 키보드를 함께 지원한다 |
| date-fns | 나이 계산, 최근 4주 출석 범위 계산 |
| Vitest + React Testing Library, Playwright | 컴포넌트·훅은 Vitest, RLS는 로컬 Supabase 대상 통합 테스트, 핵심 흐름 3개만 Playwright |
| vite-plugin-pwa + web-push (Edge Function) | PWA 설치 사용자와 웹 푸시 지원 브라우저에만 알림을 보낸다 |

## 데이터 모델 개요

| 테이블 | 책임 |
|---|---|
| `profiles` | 이름·성별·생년월일·휴대폰, 항목별 공개 플래그, 역할, 마지막 접속 시각 |
| `cohorts` | 기수. 편성·출석·주문 기록의 보관 단위 |
| `villages` | 기수에 속한 마을 |
| `village_members` | 기수별 인원 배정과 이장 여부. `village_id`가 null이면 미배정 |
| `menus` | 메뉴와 가격, 메뉴별 사용 가능 옵션(jsonb) |
| `cafe_settings` / `cafe_closures` | 주문 가능 요일·시각 / 임시 휴무일 |
| `orders` / `order_items` | 주문 묶음 / 항목. 항목에 주문 당시 메뉴명·옵션을 스냅샷으로 남긴다 |
| `attendance` | 주일 기준 예배·마을모임 출석 |
| `prayer_requests` / `village_posts` / `announcements` | 기도제목 / 마을 소식 / 전체 소식 |
| `push_subscriptions` | 웹 푸시 구독 |

**이장은 역할이 아니라 배정이다.** `village_members.is_leader`로 표현한다. "마을을 옮긴 이장은 이장 자격을 잃는다"를 트리거 한 줄로 보장할 수 있고, `profiles.role`에 두면 마을 이동과 역할 해제를 애플리케이션이 맞춰야 한다. `profiles.role`은 `admin` / `pastor` / `staff` / `youth` 네 개만 둔다.

## 권한 모델

- 모든 테이블에 RLS를 켠다. 판단 로직은 `SECURITY DEFINER` 헬퍼 함수(`is_admin_or_staff()`, `is_pastor()`, `is_leader_of(village)`, `active_cohort_id()`)에 모아 정책에서 호출한다.
- **쓰기 중 시간·권한 검증이 필요한 것은 RPC로 감싼다.** 주문 제출·취소는 `place_order` / `cancel_order_item`을 거친다. 마감 검증을 클라이언트 시계에 맡기지 않기 위해서다.
- **게스트는 테이블에 직접 접근하지 않는다.** `anon`에는 RPC 실행 권한만 준다(`place_order`, `get_guest_orders`, `cancel_order_item`). 확정한 식별 방식: 최초 주문 시 UUID를 발급해 localStorage에 저장하고 주문 행에 함께 넣는다. RPC 인자의 토큰이 일치할 때만 조회·취소를 허용하고, 유효 범위는 그날 마감 시각까지다.
- **가격 비노출은 뷰로 처리한다.** `menus`는 관리자만 select 하고, 청년·게스트는 가격 컬럼이 없는 `menus_public` 뷰만 본다. 컬럼을 숨기는 일을 UI에 맡기지 않는다.
- **개인정보 마스킹도 뷰로 처리한다.** 마을원 명단은 공개 플래그를 적용한 뷰로 내려간다. 관리자용 뷰는 원본을 내려주고 마스킹 해제는 화면 토글로 한다.

## 디자인 시스템 → 코드 매핑

| 아트보드 | 코드 |
|---|---|
| 컬러 토큰, 간격·형태·모션 | `src/styles/tokens.css` — 라이트 값은 `:root`, 다크 값은 `[data-theme="dark"]`에서 같은 이름을 덮는다. 그림자 토큰은 없다 |
| 타이포그래피 | 같은 파일의 `--text-*` 10단계. 램프 밖 크기는 쓰지 않는다 |
| 컴포넌트 시트 | `src/components/ui/` — Button, Chip, Switch, Stepper, Field, Badge, Sheet, Toast, EmptyState, TabBar |
| 핵심 패턴 | 화면 조립 규칙. 주문 상태 배너, 권한 비활성 표현, 마스킹 토글, 편성 두 경로 |
| 모바일·PC 화면 | `src/features/*/` 각 페이지의 기준 시안 |

층위는 테두리나 그림자가 아니라 면의 밝기 차이로 만든다(애플 그룹 리스트 방식). 컨테이너에 `border`를 두르거나 `box-shadow`를 넣는 코드는 리뷰에서 되돌린다. 헤어라인(`--separator`)은 그룹 리스트 안쪽에서 행을 나눌 때만 쓴다.

## 단계

각 단계는 배포 가능한 상태로 끝난다.

### 1단계 — 기반과 게스트 주문 (상세 계획: `2026-08-31-phase1-guest-ordering.md`)

프로젝트 셋업, 디자인 토큰과 기본 컴포넌트, Supabase 스키마 1차와 RLS, 주문 RPC, 주문·옵션 시트·내 주문 화면, Vercel 배포.

**완료 조건:** 로그인 없이 메뉴를 골라 주문하고 마감 전까지 취소할 수 있다. 마감 후에는 주문과 취소가 DB에서 막힌다. 라이트·다크 테마가 저장되고 복원된다.

### 2단계 — 인증과 내 정보

카카오 OAuth, 로그인 시 `profiles` 생성과 `last_seen_at` 기록, 내 정보 조회·수정, 항목별 공개 설정, 로그인 사용자의 주문 내역(기수별 보관), 역할 배지, 역할 변경 시 화면·장바구니·탭 초기화.

**완료 조건:** 카카오로 로그인한 청년이 자기 주문 내역을 이어서 보고, 공개 설정을 바꿀 수 있다. 게스트 경로는 그대로 동작한다.
**의존:** 1단계의 `orders.profile_id` 경로.

### 3단계 — 마을

기수·마을·배정 스키마 완성, 내 마을(명단·오늘 출석·소식·기도제목), 이장 기능(예배·마을모임 출석 체크, 최근 4주 수정 제한, 마을명 변경, 마을 소식 발행, 내 마을 주문 통계).

**완료 조건:** 이장이 출석을 체크하고 소식을 올리며, 마을원이 명단·출석·기도제목을 본다. 다른 마을 데이터는 RLS에서 막힌다.
**의존:** 2단계의 인증과 `profiles`.

### 4단계 — 운영

전체 명단 CRUD, 마을 생성·삭제, 편성 화면(드래그앤드롭 + 선택 후 이동), 마을별 남녀 비율·평균 나이, 이장 지정·해제(목회자), 역할 지정, 1년 미접속자 목록과 삭제, 카페 운영(주문 현황 2화면, 메뉴 관리, 주문 시간 설정, 임시 휴무), 전체 소식.

**완료 조건:** 목회자·임원이 한 해 편성을 처음부터 끝까지 진행하고, 주일 주문 현황을 마을별로 확인한다.
**의존:** 3단계의 마을 스키마.

### 5단계 — 알림과 PWA

PWA 설치, 웹 푸시 구독 관리, 마을 소식·전체 소식 발행 시 Edge Function으로 발송, 미지원 환경에서 알림 항목 숨김.

**완료 조건:** 설치한 사용자가 마을 소식 알림을 받는다. 미지원 브라우저에서는 알림 설정이 보이지 않는다.
**의존:** 3·4단계의 소식 발행.

## 이번에 확정한 것

- **Supabase는 새 프로젝트로 만든다.** 스키마와 RLS를 처음부터 설계하고 기존 서비스에 영향을 주지 않기 위해서다. 기존 주문 데이터를 옮길 필요가 생기면 1단계 이후 별도 이관 작업으로 다룬다.
- **게스트 식별은 익명 토큰 방식으로 한다.** Supabase 익명 로그인은 계정이 계속 쌓여 정리 작업이 필요하고, 이 앱의 게스트는 그날 하루만 자기 주문을 보면 된다.
