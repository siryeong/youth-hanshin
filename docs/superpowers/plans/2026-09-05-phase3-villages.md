# 3단계 마을 구현

로그인한 사용자는 `/village`에서 소속 마을의 명단·출석·소식·기도제목을 조회합니다. 이장은 마을명과 소식을 관리하고 최근 4주 출석을 수정합니다. 전체 관리자는 모든 마을을 조회합니다.

## 구현 범위

- 기수별 마을·배정, 미배정 상태, 여러 이장 지원
- 공개 설정을 반영한 명단과 개인정보 마스킹 해제
- 주일별 예배·마을모임 출석, 현재 주일을 포함한 4주 수정 제한
- 이장의 마을명 변경과 소식 등록·수정·삭제
- 마을원의 기도제목 등록과 본인 글 수정·삭제
- 이장·전체 관리자의 마을 주문 통계, 취소 항목 제외
- 지난 기수 명단·출석·소식·기도제목 조회
- 마을 이동·권한·공개 설정·내용 변경 시 재조회

## 결정과 이유

| 결정 | 이유 |
|---|---|
| 한 마을 화면에 조회와 이장 기능 배치 | [Planning Center Groups](https://help.planningcenter.com/en/138443-introduction-for-group-leaders.html)의 그룹별 명단·출석·소식 관리 방식과 기존 `design/MyVillage.dc.html` 시안 적용 |
| 기수·회원 조합으로 배정을 식별하고 마을 이동 시 이장 해제 | 중복 배정을 막고 지난 기수 배정 보존 |
| 개인정보를 마스킹한 뷰에 명시적 조회 조건과 SELECT 권한만 부여 | 원본 프로필의 접근 범위를 넓히지 않고 공개 필드만 제공. [Supabase RLS 지침](https://supabase.com/docs/guides/database/postgres/row-level-security) 적용 |
| 출석 변경은 RPC로 처리 | 서울 시간의 최근 주일부터 21일 전까지 주일 4개만 허용. 예배·모임 중 변경한 항목만 저장 |
| 지난 기수는 조회만 허용 | 보관 기록의 변경 방지 |
| 주문 생성 시 마을 ID 기록 | 이후 인원 이동으로 과거 주문 집계가 바뀌는 문제 방지. 기존 주문의 소속 마을은 추정하지 않음 |
| 본인 프로필의 `village_revision`을 Realtime으로 수신 | 이동 후 이전 마을의 SELECT 권한을 잃어도 본인에게 변경 전달. 마을 데이터 자체를 다른 구독자에게 전송하지 않음 |
| 기존 React Query·기본 폼·CSS 사용 | 추가 의존성 없이 조회·변경·입력 검증과 반응형 화면 구현 |

## 반영과 검증

추가 마이그레이션은 `0009_order_identity.sql`, `0010_villages.sql`입니다. `0009`는 회원의 게스트 토큰 취소 경로와 게스트 조회 RPC 접근을 차단합니다. `0010`은 마을 스키마·권한·변경 알림을 추가합니다.

`npm run test:db:village`는 실행 중인 로컬 `supabase_db_youth-hanshin-v2` 컨테이너에서 SQL 권한·제약·인증·주문 회귀를 검증합니다. 새 스키마와 합성 데이터를 한 트랜잭션 안에서 사용하고 롤백합니다. DB 초기화와 환경 파일이 필요하지 않습니다.

`npm run test:ui`는 외부 인증/API를 모킹해 마을 관리, 출석·글 저장 실패, 입력 보존, 기수 전환, 이장 해제·미배정 갱신과 모바일·다크 화면을 검증합니다. 실제 Realtime 전송은 이 브라우저 테스트에 포함하지 않습니다.

운영 DB에는 이번 마이그레이션을 적용하지 않았습니다. 기수 생성·마을 생성·인원 배정·이장 지정 UI는 4단계에서 구현합니다. 배정 데이터가 없으면 [내 마을]에 미배정 안내를 표시합니다.
